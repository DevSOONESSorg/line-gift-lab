# 職員向けガイド

## 事前準備

- 参加者用PCに Docker Desktop を入れ、**事前に一度 `docker compose up` と `docker compose --profile tunnel pull`** をしておく（当日のダウンロード待ちをなくす）
- 事業所のネットワークで `*.trycloudflare.com` が使えるか確認（コースB3以降）。使えない場合は、B1・B2 までで区切るか、ngrok など別のトンネルを職員が用意する
- 障害ドリルの症状カード（下の表の「症状カード」列）を印刷しておく
- コースBは、参加者本人のLINE（方法A）か、メールアドレスで作るビジネスID（方法B）を使う。どちらにするかは前日までに本人に確認

## タイムテーブル例（1日4時間 × 2〜3日）

| 日 | 内容 |
|---|---|
| 1日目 | 起動 → 第0章 → 第1〜2章（全店舗共通）→ 第3〜6章（オリジナルの構築：つなぐところまで） |
| 2日目 | 第7〜10章 → 障害ドリル → 通しチェック・提出 |
| 3日目 | コースB（B0〜B2 は全員、B3 以降は進める人だけ）→ 片付け |

進みが早い人は、2日目の午後からコースBへ。コースAを飛ばして、いきなりコースBから始めるのはおすすめしません（コースBで詰まったとき、裏側を想像できないため）。

## 声かけのポイント

- 最初に「**オーナー・お客さん・運営スタッフ**」の3つの役割を確認する。教材では疑似スマホ1台で、オーナーとお客さんの両方を演じる。本物の運営スタッフがスマホを触るのは動作確認のときだけ

- 詰まったら、まず「**裏側ビューで NG の行はある？**」と聞く。答えを言わずに、見る場所を示す
- 「なぜ？」の節は、読むだけでなく **自分の言葉で説明してもらう**（隣の人・職員に）
- 1人2役（個人アカウント／会社の作業アカウント）で混乱しやすい。画面上部の「ログイン中」を声に出して確認させる

## 障害ドリルの仕込み方

参加者が第10章まで終えたら、そのPCで職員が実行します。

```bash
docker compose exec app npm run drill -- list          # 症状カードの一覧
docker compose exec app npm run drill -- 3             # 3番を仕込む
docker compose exec app npm run drill -- random        # ランダム
docker compose exec app npm run drill -- 3 --store club-azure   # 店舗を指定
```

裏側ビューには仕込んだ記録は残りません。

### ドリルの答え（参加者に見せない）

| 番号 | 症状カード | 仕込んだ内容 | 裏側ビューのヒント | 直し方 |
|---|---|---|---|---|
| 1 | bot が返事をしない（A） | 管理画面のチャネルシークレットを1文字変えた | 自社サーバー「署名が合いません」401 | Dev Console の Channel secret を管理画面に入れ直す |
| 2 | bot が返事をしない（B） | LINE側でトークンを再発行した | 「LINEにお願い … → 401」「トークンが無効です」 | Dev Console でトークンを確認（または再発行）→ 管理画面に入れ直す |
| 3 | 返事が2通来る | 応答メッセージを ON | LINE社「応答メッセージ（定型文）を自動で返しました」 | Manager 応答設定で応答メッセージ OFF |
| 4 | bot が返事をしない（C） | Webhook URL の slug を打ち間違えた | 自社サーバー「○○という slug の店舗はありません」404 | Dev Console の Webhook URL を直す → Verify |
| 5 | ちがうお店が開く | LIFF のエンドポイントURL を見本カフェにした | 自社サーバー「LIFF ○○ から見本カフェの画面が開かれました」 | Dev Console の LIFF タブでエンドポイントURLを直す |
| 6 | 何も買えない（A） | 承認を外した | 「まだ承認されていないので表示しません」 | 管理画面で承認済みに |
| 7 | 何も買えない（B） | 商品を全部削除した | （NGなし）画面に「商品がありません」 | オーナー役で店舗管理から商品を登録（または店舗詳細で追加） |
| 8 | リッチメニューの「贈る」でエラー | リッチメニューの LIFF ID を1文字変えた | LINE社「LIFF ID ○○ は見つかりません」 | Manager でリッチメニューを作り直す（正しい LIFF ID） |
| 9 | お知らせが届かなくなった | 疑似スマホで店舗の公式アカウントをブロック状態にした | LINE社「200 でも届いていません（友だちではない／ブロック中）」 | 疑似スマホのトーク右上「ブロック解除」 |

## チェック問題の答え

| 章 | 答え |
|---|---|
| 1 | ①オーナー ②オーナー（運営は代わりに入れることがあるだけ） ③LIFFのエンドポイントURL・Webhook URL と食いちがい、つながらなくなる ④共通掲載の一覧に出ず、贈る画面は「準備中」になる |
| 2 | ①750円 ②変わらない（注文時に計算して保存している） ③いらない（承認・手数料だけ） |
| 3 | ①管理者 ②リッチメニュー・応答設定・Messaging API が扱えれば作業できるから（メンバー追加などは不要。必要最小限の権限にする） ③会社のアカウントからチャネルが「権限なし」で開けない／運営のプロバイダーと箱がちがうので、ユーザーIDが運営側とそろわない |
| 4 | ①`https://liff.line.me/…` ②別のお店の贈る画面が開く |
| 5 | ①チャネルID・チャネルシークレット・アクセストークン ②トークン ③LINEへのお願い（返信・送信）が 401 で失敗する |
| 6 | ①送る＝LINE社、受け取る＝自社サーバー ②シークレットの食いちがい ③URL の slug |
| 7 | ①Manager の応答設定の応答メッセージ ②応答モードが Bot か／Webhook がオンか／（Messaging API が有効か） |
| 8 | ①2500×1686・1200×810・800×540 のどれか ②リンクで `https://liff.line.me/{LIFF_ID}` |
| 9 | ①200円 ②不具合ではない（仕様） |
| 10 | ①オーナーの「受け取る」 ②運営の公式LINE。そのお客さんが確実に友だちなのは、使った入口の公式LINEだから ③カードの目印（下4桁・有効期限。本物は決済会社のカードID） ④その公式アカウントと友だちでない（ブロック中）／トークンが無効 |

## 提出物の受け取り

- コースA：通しチェックのキャプチャ、障害ドリルの報告、感想
- コースB：スマホのキャプチャ、作業報告、（B3以降）`git diff` のファイル
- 疑似LINEのデータを丸ごと見たいときは、参加者の `data/` フォルダ（`app.db`・`mock-line.db`・`inside.db`）を Slack で提出してもらう

## 片付け

- コースB を行った人は、**B9 片付け** を職員の前で行ってもらう（公式アカウント・チャネル・プロバイダーの削除）
- PC を次の人に渡す前に `docker compose run --rm app npm run reset`、`.env` の削除
